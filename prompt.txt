Phase 2: aspect calculation (pure functions, no DB)


New module aspects.py:

Experience levels. level(xp, K) = xp / (xp + K) with a K per skill track and a default for tools.
Formula. final[a] = base[a] × attribute[a] × tool[a] × exp[a].
Intensity’s base is metabolic_mult and the other three start at 1.0.
exp[a] = max(floor, 1 + exp_coeffs[a] × skill_level).
Tool realization.
tool_level = max(familiarity, transfer × skill_level).
Only the favorable part of a tool multiplier is scaled by floor + (1 − floor) × tool_level. Penalties from a worn tool aren’t softened by familiarity.
“Favorable” depends on direction: for intensity, lower is better, and for the others, higher. Keep a single shared ASPECT_DIRECTION constant.
Multiple tools. Enforce a single tool in the UI for now. The aggregator takes the best per aspect, so a list works later without redesign.
Output. An AspectBreakdown with base, attribute, tool, exp and final per aspect, with to_json. It’s stored in snapshots so the GM can see why safety was low.
Tests. Same axe, novice versus expert. Blunt versus sharp. No tool. Monotonicity in sharpness and skill. Direction sanity for intensity.


Phase 3: contexts (chopping slice only)


TaskContext contains task facts (preset name, activity, skill track, progress fraction, min_lighting), a SiteContext, a ParticipantContext and misfortune.
ParticipantContext holds the AspectBreakdown, the skill level, an optional ToolContext (condition, wet, familiarity), and the stats and attributes as mappings.
SiteContext for now has illumination and clearance (0 to 1, open to cramped), plus a lighting_deficit helper in the same units as min_lighting.
Misfortune convention. misfortune ∈ [0, 1), higher is worse, and a technicality fires when misfortune ≥ 1 − p. It comes from a deterministic keyed roll over (seed, task, participant, tick, technicality key), and the machine injects it with dataclasses.replace.
Gatherers. gather_task_shared runs once per task per tick and resolves the preset once. gather_participant runs per participant. Both read from state and take fakes in tests.
Every snapshot type gets to_json, and items carry a kind tag.


Phase 4: triggers (technicalities.py)


A registry decorator @trigger(handle) that rejects duplicate handles and exposes list_handles() for the UI dropdown.
The core function is fire_probability(base_risk, k, safety, exposure):
odds = base_risk / (1 − base_risk), scaled by exposure / max(safety, floor) ** k, then p = odds / (1 + odds).
The safety floor avoids infinity as safety approaches 0.
Each handle is registered from a factory that fixes base_risk, k and the exposure terms (clearance, lighting deficit). These are per-profile handles, which is the price of not having params. Name them by mechanism and profile, such as safety_gated_clearance_strong.
Each registry entry holds an explain(ctx) function that returns (fired, p, factors). The public trigger is its boolean, so your signature is unchanged, and the machine stores the factors in context_snapshot.
Tests. Print a table of p over skill and clearance and assert it’s monotonic. Check the roll is deterministic. Check the empirical fire rate over many seeds is close to p.

Describing the progress event (not implemented)

A TaskProgressEvent handles one active task per tick, in one transaction:

Load the task and participations, and skip participants blocked by a complication.
Recompute each participant’s AspectBreakdown.
Convert efficiency into workload for the tick. Contributions accumulate in workload_buffer and merge into workload_done at the end of the tick, so every participant sees the same “before” value for crossing checks. This is my assumption about workload_buffer, so correct me if it means something else.
Append contribution_ledger entries (amount and quality contribution).
Apply side effects: fatigue from intensity, tool wear on durability and sharpness, and experience gain for skill and tool.
Evaluate due technicalities (crossing detection for once, rate-normalized for constant), with one keyed roll per participant and technicality. A hit creates a ProblemFiring plus a Complication and sets the participant’s blocked_by.
If workload_done ≥ total, run the once checks at 1.0 first, then move the task to an “awaiting GM” status, not “done”. The GM’s quality mapping creates the output, and then the task closes and the tools are released.
Emit follow-up events (TaskCompleted, ComplicationRaised) and reschedule itself while the task is active.

Because rolls are keyed and deterministic, retrying a failed tick gives the same outcome.
